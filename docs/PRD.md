### 1.1 용어 정의

| 용어 | 정의 |
| --- | --- |
| **프로젝트** | 하나의 서비스/화면에 대한 의사결정 단위. 분야, 키워드, 단계별 선택값, 최종 산출물을 묶는다. |
| **단계(Step)** | 컨셉 → 컬러 팔레트 → 와이어프레임 → 컴포넌트 세트 → 프로토타입 이미지 순의 확정 단위. |
| **선택 확정(Commit)** | 해당 단계 후보 중 1개를 프로젝트에 고정하는 행위. 이후 단계는 확정된 컨텍스트만 사용한다. |
| **생성(Generation)** | AI가 후보 또는 최종 이미지를 새로 만드는 요청 1회. |
| **크레딧** | 생성 요청을 계량하는 내부 화폐. 생성 1회 = N 크레딧(섹션 7.1 규칙). |
| **프로토타입 이미지** | 앞 단계 확정값을 반영한 **최종 시각 산출물**. 첫 단계가 아니다. |
| **컨텍스트 누적** | 이전 단계에서 확정한 값을 다음 단계 프롬프트/입력에 반드시 포함하는 방식. |

### 1.2 기술 가정 (제품 관점 우선, 구현 제약은 가정)

- **가정**: 웹. 프론트는 Next.js 14 App Router, TypeScript, TailwindCSS, Shadcn UI, Radix. React Server Components 우선.
- **단계 분리**: 1차 구현(프로토타입)은 인증·Supabase·DB 스키마·크레딧 원장 없이 워크플로와 생성 파이프라인만 만든다. 데이터·인증·스키마는 **상용화(다음 개발)** 에서 Supabase로 붙인다.
- API 계약, 이미지 모델 벤더는 본 PRD에서 확정하지 않는다. 필요 시 기술 스파이크.

## 2. 문제 정의 / 기회

### 2.1 현재 상황

초기 제품의 UI를 잡을 때 기획자·창업자·개발자·디자이너는 레퍼런스 수집, 무드보드, 컬러, 레이아웃, 컴포넌트 스타일을 **서로 다른 도구와 대화 스레드**에서 병렬로 진행한다. 합의 전에 고해상도 목업을 먼저 만들면 “예쁜 화면”만 남고, 왜 그 컨셉인지에 대한 의사결정 기록이 없다.

그린필드이며 기존 코드베이스/레거시 워크플로는 없다. 빈 화면에서 **의사결정 순서를 제품이 강제**할 수 있다.

### 2.2 해결하려는 문제

1. **합의 비용**: “이 톤이 맞는지”를 말로 반복하면 사이클이 길어진다. 선택지가 시각화되지 않으면 반려 이유가 모호하다.
2. **순서 역전**: 최종 이미지부터 생성하면 컬러·레이아웃·컴포넌트가 사후에 끼워맞춰진다. 재생성 비용이 크고, 이전 선택을 재사용할 수 없다.
3. **산출물 단절**: 컨셉/팔레트/와이어프레임/컴포넌트가 파일·슬랙·노션에 흩어져 같은 프로젝트를 다시 열 수 없다.
4. **역할 간 번역 비용**: 기획 키워드 ↔ 디자인 토큰 ↔ 개발 컴포넌트 이름이 맞지 않아 핸드오프가 반복된다.

### 2.3 왜 지금인가

- 생성형 이미지는 품질이 올랐으나, **단계 없는 원샷 생성**은 초기 기획 합의에 오히려 노이즈가 된다.
- 스타트업·사이드프로젝트는 전담 디자이너 없이 첫 화면을 빨리 맞춰야 한다.
- 기회: “예쁜 이미지 생성기”가 아니라 **시각적 의사결정 워크플로우 + 최종 이미지**로 포지셔닝하면 차별화가 가능하다.
- 리스크: 이미지 생성 단가·저작권·품질 편차가 브랜드를 훼손할 수 있다. 따라서 이미지는 **마지막 단계**로 고정한다.

### 2.4 Positioning (한 줄)

분야와 키워드로 시작해, 컨셉·컬러·와이어프레임·컴포넌트를 **한 단계씩 보고 고른 뒤**, 그 확정값으로만 최종 UI 프로토타입 이미지를 만든다.

## 3. 목표와 비목표

### 3.1 목표 (Goals)

**1차 구현 (프로토타입, 지금)**

1. 로그인 없이 **60분 이내**에 프로젝트 1개를 만들고, 4개 중간 단계(컨셉/컬러/와이어프레임/컴포넌트)를 각각 최소 1회 확정한 뒤, 최종 프로토타입 이미지 1장을 볼 수 있다.
2. 최종 이미지는 **직전 확정 단계의 컨텍스트가 모두 채워진 상태**에서만 요청할 수 있다. 중간 단계 스킵으로 최종 생성에 진입할 수 없다.
3. 같은 브라우저 세션(또는 localStorage)에서는 단계별 선택값과 최종 이미지를 다시 볼 수 있다. 서버 영속·계정 연동은 보장하지 않는다.

**상용화 (다음 개발)**

4. 저장된 프로젝트는 **로그아웃 후 재로그인**해도 단계별 선택값과 최종 이미지를 동일하게 재조회할 수 있다.
5. 모든 생성 요청은 **크레딧 잔액이 충분할 때만** 실행되며, 잔액 부족 시 생성하지 않고 잔액·필요 크레딧을 화면에 표시한다.
6. 출시 후 4주 내, 최종 이미지까지 완료한 프로젝트 중 **재방문 7일 내 동일 프로젝트 재오픈 비율**을 측정 가능한 이벤트로 수집한다.

### 3.2 비목표 (Non-goals) — 1차 구현에서 하지 않음

- **인증/세션, Supabase, DB 스키마, RLS, 크레딧 원장, 서버 영속 저장** — 상용화(다음 개발).
- 완성된 프로덕션 프론트엔드 코드(React/Vue 컴포넌트 소스) 자동 생성 및 저장소 연동.
- Figma 플러그인 네이티브 편집, Dev Mode 양방향 동기화 (v1.1은 링크/토큰 내보내기까지만).
- 실시간 멀티플레이어 캔버스 편집 (Figma/FigJam 대체).
- 사용자 업로드 디자인 시스템·브랜드 가이드 **학습**(P2).
- 모바일 네이티브 앱, 오프라인 전용 모드.
- 결제 게이트웨이 실연동 — **P1**. 크레딧 규칙·원장은 상용화.
- 다국어 UI 전체 제공 — 1차는 **한국어 UI 우선**.
- 법적 자문 확정 수준의 저작권 면책. 제품 안전 가드레일만 명시하고 약관 문구는 법무 검토.

## 5. 핵심 가치 제안과 차별점

### 5.1 가치 제안 (관찰 가능한 결과)

사용자는 텍스트 한 방이 아니라 **단계마다 후보를 보고 1개를 확정**한다. 시스템은 확정된 값만 다음 단계에 넘긴다. 최종 이미지는 그 체인의 결과물이다.

검증 포인트:

- 최종 생성 버튼은 4개 중간 단계가 모두 `committed`일 때만 활성.
- 프로젝트 상세는 단계별 확정 스냅샷(선택 ID, 시각 프리뷰, 확정 시각)을 보여 준다.
- 같은 확정 세트에서 최종 이미지를 다시 열면 메타데이터에 사용된 컨셉/팔레트/와이어프레임/컴포넌트 ID가 남아 있다.

### 5.2 차별점

| 구분 | 원샷 이미지 생성 툴 | 본 제품 |
| --- | --- | --- |
| 시작점 | 긴 프롬프트 또는 레퍼런스 이미지 | 서비스 분야 + 키워드 |
| 의사결정 | 결과 이미지 평가 | 단계별 후보 비교·확정 |
| 재현성 | 프롬프트 재입력에 의존 | 프로젝트에 선택 이력 저장 |
| 최종물 | 이미지가 곧 작업물 | 이미지는 확정 체인의 마지막 산출물 |
| 개발 핸드오프 | 약함 | 와이어프레임·컴포넌트 세트가 중간 산출물 (내보내기는 P1) |

### 5.3 하지 않는 약속

- “디자이너를 대체한다”고 주장하지 않는다. 초기 합의와 탐색 시간을 줄인다.
- 픽셀 퍼펙트 디자인 시스템 준수를 MVP에서 보장하지 않는다.
- 생성 이미지가 상용 출시 UI와 동일하다고 보장하지 않는다.

## 6. 사용자 여정 (단계별 워크플로우)

핵심 원칙: **이미지는 최종 산출물이지 첫 단계가 아니다.** 각 단계는 (1) 생성 또는 후보 표시 → (2) 비교 → (3) 1개 확정 → (4) 다음 단계 잠금 해제.

### 6.1 엔드투엔드 플로

```
(1차: 로그인 없음)
온보딩(선택)
  → 프로젝트 생성(이름)
  → 분야 + 키워드 입력·저장
  → [1] 디자인 컨셉 추천 → 1개 확정
  → [2] 컬러 팔레트 추천 → 1개 확정
  → [3] 와이어프레임 추천 → 1개 확정
  → [4] 컴포넌트 세트 추천 → 1개 확정
  → [5] 프로토타입 이미지 생성
  → 같은 브라우저에서 재조회 (localStorage)

상용화: 앞에 가입/로그인, 뒤에 서버 히스토리 재조회를 붙인다.
```

### 6.2 단계 상세

**0. 입력 — 분야 / 키워드**  
- 사용자는 서비스 분야(예: 헬스케어, 핀테크, 이커머스, 교육, 사내툴)와 키워드(톤, 타깃, 화면 종류)를 입력한다.  
- 이 값은 이후 모든 단계의 공통 컨텍스트가 된다. 변경 시 **미확정 이후 단계만** 무효화할지, 전 단계 재확정이 필요한지는 섹션 15.

**1. 컨셉 추천**  
- 분야+키워드 기준으로 컨셉 후보 N개(기본 3)를 보여 준다. 각 후보는 이름, 한 줄 포지션, 비주얼 힌트(무드 썸네일 또는 스타일 칩).  
- 사용자는 1개를 확정한다. 확정 전에는 최종 이미지 생성 불가.

**2. 컬러 팔레트**  
- 확정 컨셉 + 분야/키워드를 입력으로 팔레트 후보 N개. 각 팔레트는 역할이 붙은 색 슬롯(예: primary, secondary, background, text, accent)과 미리보기.  
- 1개 확정.

**3. 와이어프레임**  
- 확정 컨셉·팔레트·화면 키워드를 반영한 **구조 중심** 후보. 컬러가 입혀지더라도 목적은 레이아웃·정보 계층이다.  
- 1개 확정.

**4. 컴포넌트 조합**  
- 확정된 와이어프레임 슬롯에 맞는 컴포넌트 세트(버튼, 입력, 카드, 네비게이션 등) 후보.  
- 1개 확정.

**5. 프로토타입 이미지 생성**  
- 위 확정값만으로 최종 UI 프로토타입 이미지를 생성한다.  
- 결과는 프로젝트에 저장되고 히스토리에서 다시 연다.

### 6.3 사용자 스토리

1. **As a** 기획자, **I want** 컨셉 3안을 나란히 보고 1개를 확정하고 싶다, **so that** 미팅에서 “방향 A”를 프로젝트 링크로 재현할 수 있다.  
2. **As a** 창업자, **I want** 분야와 키워드만 넣고 단계별로 고르고 싶다, **so that** 디자이너 없이 당일 프로토타입 이미지 1장을 남길 수 있다.  
3. **As a** 프론트엔드 개발자, **I want** 와이어프레임과 컴포넌트 세트가 이미지보다 먼저 확정되길 원한다, **so that** 구현 범위와 토큰 논의를 이미지 취향 논쟁과 분리할 수 있다.  
4. **As a** 디자이너, **I want** 이전 단계 확정을 유지한 채 한 단계만 다시 생성하고 싶다, **so that** 전체 파이프라인을 처음부터 돌리지 않는다.  
5. **As a** 사용자, **I want** 같은 브라우저에서 어제 만든 프로젝트를 다시 열고 싶다, **so that** 데모 중 합의 기록을 잃지 않는다. (계정 연동 재조회는 상용화)

### 6.4 단계 재생성 규칙 (P0 동작)

- 이미 확정된 단계를 **재생성**하면, 그 단계의 기존 확정은 `superseded`가 되고 이후 단계 확정은 **무효(stale)** 가 된다.  
- stale 단계가 있으면 최종 이미지 생성은 막고, 사용자에게 “이후 단계를 다시 확정하라”고 표시한다.  
- 미확정 단계에서 후보만 다시 받는 것은 이후 단계에 영향을 주지 않는다(확정 전이므로).

## 7. 기능 요구사항

우선순위: **P0-proto = 1차 구현**, **P0-ga = 상용화(다음 개발)**, **P1 = v1.1**, **P2 = v2**.

크레딧 **제품 규칙·원장**과 **인증·Supabase**는 P0-ga. **결제 수단 연동**은 P1. 1차 구현은 생성 제한 없이 워크플로를 검증한다.

### 7.0 크레딧 제품 규칙 (P0-ga, 전 기능 공통 — 1차 구현 제외)

**가정(기본값, 미결 시 이 값 사용)**

| 생성 유형 | 크레딧 N | 비고 |
| --- | --- | --- |
| 컨셉 후보 세트 1회 (기본 3안) | 1 | 세트 단위. 안별 과금 아님 |
| 팔레트 후보 세트 1회 | 1 | |
| 와이어프레임 후보 세트 1회 | 2 | 구조 생성 비용 가정 |
| 컴포넌트 세트 후보 1회 | 2 | |
| 최종 프로토타입 이미지 1장 | 5 | 최종 산출물 |
| 단계 재생성 | 해당 단계와 동일 N | 변형(variant)은 P1, 동일 N |

- 신규 계정 가입 시 **무료 크레딧 20**을 지급한다(가정). 20은 컨셉+팔레트+와이어+컴포넌트+최종 이미지 1사이클(1+1+2+2+5=11)과 여유 재생성을 커버한다.  
- 잔액 `< N`이면 해당 생성은 **호출되지 않는다**. 버튼은 비활성 또는 클릭 시 잔액 부족 패널(필요 N, 현재 잔액, 유료 안내).  
- 생성 **요청이 서버에서 수락된 시점**에 크레딧을 선차감한다. 시스템 실패로 후보/이미지가 0건이면 **전액 환급**한다. 사용자가 결과를 마음에 안 들어 하는 것은 환급하지 않는다.  
- 동일 확정값으로 결과 화면을 **다시 보기만** 하는 조회는 크레딧을 쓰지 않는다.  
- 크레딧 원장은 사용자별로 불변 로그(차감/환급/지급, 사유, 프로젝트 ID, 생성 ID, 시각)을 남긴다.  
- 유료 구독·크레딧 팩 **구매 결제**는 P1. P0에서는 운영자가 confer(지급)하거나 시드 크레딧만으로 테스트 가능하다. UI에는 “유료로 충전(준비 중 또는 P1)” 진입점을 둘 수 있다.

### 7.1 P0-proto — 1차 구현 Must

워크플로·생성 UI만. 로그인 없음. 프로젝트 상태는 브라우저(localStorage)에만 둔다.

아래 P0-ga 항목은 1차에서 구현하지 않는다: 인증, 서버 저장, 크레딧 원장, 타인 프로젝트 격리, 계정 원장 화면.

### 7.1a P0-ga — 상용화 Must (다음 개발)

#### P0-1. 인증 (로그인 / 세션)

로그인하지 않은 사용자는 프로젝트를 생성·조회·생성 요청할 수 없다. 이메일 매직링크 또는 이메일+비밀번호 중 1개 이상을 제공한다(**가정**: Supabase Auth).

**수용 기준**

- Given 비로그인 사용자가 프로젝트 생성 URL에 접근할 때, When 페이지를 열면, Then 로그인 화면으로 보내고 프로젝트는 만들어지지 않는다.  
- Given 유효한 계정으로 로그인한 사용자가, When 세션이 유지되는 동안 프로젝트를 열면, Then 본인 소유 프로젝트만 보인다.  
- Given 로그아웃한 사용자가, When 보호된 페이지를 요청하면, Then 데이터를 보여 주지 않고 로그인으로 보낸다.

#### P0-2. 온보딩 / 프로젝트 생성

첫 로그인 시 3단계 이내 안내: (1) 단계형 워크플로우, (2) 이미지는 마지막, (3) 크레딧 잔액. 사용자는 프로젝트 이름(1~80자)으로 프로젝트를 만든다.

**수용 기준**

- Given 가입 후 첫 세션에서, When 온보딩을 완료하거나 건너뛰면, Then 빈 프로젝트 목록 또는 생성 CTA가 보인다.  
- Given 로그인 사용자가 유효한 이름을 제출하면, When 생성이 성공하면, Then 프로젝트 상세(입력 단계)로 이동하고 목록에 즉시 나타난다.  
- Given 이름 미입력 또는 81자 이상이면, When 제출하면, Then 서버/클라이언트 모두 생성하지 않고 오류를 보여 준다.

#### P0-3. 분야 + 키워드 입력

프로젝트당 분야 1개(프리셋 선택 또는 직접 입력), 키워드 1개 이상. 키워드는 쉼표/칩으로 3~10개를 권장하되 **최소 1개, 최대 15개**, 각 키워드 2~30자.

**수용 기준**

- Given 프로젝트 상세에서, When 분야와 키워드를 저장하면, Then 이후 컨셉 생성에 해당 값이 사용되고 화면에 요약이 남는다.  
- Given 키워드 0개인 상태에서, When 컨셉 생성을 누르면, Then 생성 호출 없이 입력 오류를 보여 준다.  
- Given 저장된 입력값이 있을 때, When 프로젝트를 다시 열면, Then 동일 분야·키워드가 복원된다.

#### P0-4. 단계별 추천 — 컨셉 / 컬러 / 와이어프레임 / 컴포넌트

각 단계는 직전 단계가 확정된 뒤에만 생성 가능하다. 단계당 후보는 **기본 3개**, 한 화면에 비교 가능하다. 각 후보는 제목, 짧은 설명, 시각 프리뷰를 가진다.

**수용 기준**

- Given 분야·키워드가 저장된 프로젝트에서, When 컨셉 생성을 요청하고 크레딧이 충분하면, Then 3개 컨셉 후보가 표시되고 1크레딧이 차감된다(실패 시 환급).  
- Given 컨셉 미확정 상태에서, When 팔레트 생성을 요청하면, Then 호출되지 않고 “컨셉을 먼저 확정하라”고 표시한다. 컬러→와이어, 와이어→컴포넌트도 동일.  
- Given 생성 중이면, When 사용자가 같은 단계 생성을 다시 누르면, Then 중복 차감 없이 진행 중 상태를 유지하거나 무시한다(이중 제출 방지).  
- Given 후보가 화면에 있으면, When 사용자가 확정 없이 새로고침하면, Then 미확정 후보는 재조회되거나 “다시 생성” CTA가 보이며, 확정 전 휘발 정책은 일관되어야 한다(**가정**: 마지막 생성 후보는 프로젝트에 임시 저장).

#### P0-5. 선택 확정 (Commit)

단계당 확정은 1개. 확정 시 타임스탬프와 선택 ID를 저장한다. 확정 변경은 섹션 6.4대로 이후 단계를 stale 처리한다.

**수용 기준**

- Given 컨셉 후보 3개가 있을 때, When 사용자가 2번 후보를 확정하면, Then 해당 후보가 `committed`로 표시되고 팔레트 단계가 잠금 해제된다.  
- Given 팔레트가 이미 확정된 뒤, When 컨셉을 다른 후보로 재확정하면, Then 팔레트·이후 단계는 stale이고 최종 생성은 비활성이다.  
- Given 확정된 단계가 있으면, When 프로젝트를 재조회하면, Then 확정 프리뷰와 선택 설명이 복원된다.

#### P0-6. 최종 프로토타입 이미지 생성

4개 중간 단계가 모두 committed이고 stale이 없을 때만 최종 생성이 가능하다. 결과는 이미지 에셋 + 사용된 단계 ID 스냅샷으로 저장한다.

**수용 기준**

- Given 중간 4단계가 확정된 프로젝트에서 크레딧 ≥ 5일 때, When 최종 생성을 요청하면, Then 이미지 1장이 저장되고 5크레딧이 차감된다(실패 시 환급).  
- Given 한 단계라도 미확정 또는 stale이면, When 최종 생성 버튼을 누르면, Then 생성 호출 없이 부족한 단계 목록을 보여 준다.  
- Given 생성이 완료되면, When 결과 화면을 보면, Then 이미지와 함께 확정된 컨셉명, 팔레트 스와치, 와이어프레임/컴포넌트 요약이 같이 보인다.

#### P0-7. 결과 저장 / 재조회

최종 이미지와 단계 스냅샷은 사용자 요청 없이 생성 성공 시 자동 저장된다. 별도 “저장” 누락으로 유실되지 않는다.

**수용 기준**

- Given 최종 이미지 생성 성공 후, When 브라우저를 닫고 다시 로그인하여 해당 프로젝트를 열면, Then 동일 이미지와 단계 요약이 보인다.  
- Given 생성 중 네트워크가 끊기면, When 사용자가 프로젝트에 재진입하면, Then 진행 중/실패/완료 중 실제 서버 상태와 크레딧 원장이 모순 없이 표시된다.

#### P0-8. 프로젝트 히스토리

로그인 사용자는 본인 프로젝트 목록을 최근 수정순으로 본다. 항목당 이름, 수정 시각, 현재 단계(예: “팔레트 확정”), 썸네일(최종 이미지 또는 마지막 확정 프리뷰).

**수용 기준**

- Given 프로젝트 2개 이상이면, When 목록을 열면, Then 모두 보이고 각각 상세로 이동한다.  
- Given 다른 사용자 프로젝트 ID를 URL로 열면, When 요청하면, Then 404 또는 권한 없음이며 본문을 노출하지 않는다.  
- Given 프로젝트를 열면, When 히스토리(최소: 생성 시각, 단계 확정, 최종 생성)를 보면, Then 시간순 이벤트가 있다. MVP는 프로젝트 단위 활동 로그면 충분(팀 코멘트는 P1).

#### P0-9. 생성 로딩 / 실패 / 재시도 UI

각 생성은 로딩, 성공, 실패를 구분한다. 실패 시 사용자 메시지 + 재시도. 재시도는 새 생성으로 과금 규칙을 따른다. 시스템 폴트 환급 후 재시도는 다시 N 차감.

**수용 기준**

- Given 모델/타임아웃 실패가 나면, When 화면이 갱신되면, Then “생성 실패”와 재시도가 보이고 크레딧은 환급된 잔액을 반영한다.  
- Given 안전 필터에 걸린 입력이면, When 생성이 거절되면, Then 크레딧 미차감 또는 즉시 환급하고, 입력을 고치라는 메시지를 보여 준다(내부 모델 프롬프트는 노출하지 않음).

#### P0-10. 크레딧 잔액 표시

모든 생성 CTA 근처와 글로벌 헤더에 현재 잔액을 보여 준다. 각 버튼에 필요 크레딧 N을 표시한다.

**수용 기준**

- Given 잔액 4, 최종 생성 N=5이면, When 최종 생성 CTA를 보면, Then 비활성 또는 부족 안내이며 호출은 없다.  
- Given 차감/환급이 발생하면, When 페이지를 새로고침하지 않아도(또는 생성 완료 콜백 후), Then 잔액이 원장과 일치한다.

### 7.2 P1 — Should

#### P1-1. 변형 생성 (variant)

확정은 유지한 채, 같은 단계 제약을 두고 추가 후보 세트를 생성한다. 확정 교체 시에만 이후 단계 stale.

**수용 기준**: variant 생성도 해당 단계 N 크레딧을 쓴다. 기존 committed 후보는 유지되고 목록에 추가된다.

#### P1-2. 내보내기

- PNG: 최종 프로토타입 이미지 다운로드.  
- JSON 토큰: 확정 팔레트의 역할별 hex/rgb.  
- Figma: **가정**은 “복사용 링크 또는 수동 임포트용 JSON”이며 네이티브 플러그인은 비목표. 실현 방식은 오픈 이슈.

**수용 기준**: PNG 다운로드는 소유자만. JSON은 팔레트 committed 이후 가능. 실패 시 파일 없이 오류.

#### P1-3. 공유 링크

읽기 전용 링크. 링크로는 생성·크레딧 사용 불가. 만료 또는 해제 가능.

**수용 기준**: 링크 보유자는 확정 스냅샷과 최종 이미지를 볼 수 있고, 수정·재생성은 로그인 소유자만 가능하다.

#### P1-4. 팀 코멘트

프로젝트 단위 스레드. 단계에 핀 가능하면 좋으나 MVP+는 프로젝트 피드로도 충분.

**수용 기준**: 작성자, 시각, 본문이 저장되고 새로고침 후 유지된다. 비멤버는 작성 불가.

#### P1-5. 결제 연동

구독(월 크레딧 지급) 및/또는 크레딧 팩 구매. 웹훅으로 원장에 지급 이벤트를 남긴다.

**수용 기준**: 결제 성공 시에만 크레딧이 증가한다. 중복 웹훅은 멱등. 실패 결제는 잔액 불변.

---

### 7.3 P2 — Could

#### P2-1. 디자인 시스템 업로드  
사용 중인 컴포넌트/토큰 파일을 올려 추천을 제약한다.  
**수용 기준**: 업로드 실패 시 기존 프로젝트 확정값은 유지. 학습 실패는 생성 파이프라인을 조용히 오염시키지 않고 오류로 표시.

#### P2-2. 브랜드 가이드 학습  
PDF/URL/이미지 가이드를 요약해 전 단계 컨텍스트에 주입.  
**수용 기준**: 가이드 적용 on/off가 있고, off면 기존 분야·키워드 파이프라인과 동일.

#### P2-3. 실시간 협업  
동시 확정 충돌 방지, presence, 동시 편집.  
**수용 기준**: 동시 확정 시 마지막 쓰기 덮어쓰기 없이 conflict UI 또는 락.

## 10. AI / 생성 파이프라인 요구사항

### 10.1 프롬프트 설계 원칙

1. **단계 단일 책임**: 컨셉 프롬프트는 레이아웃 전체를 그리지 않는다. 팔레트는 화면 전체를 그리지 않는다. 와이어프레임은 비주얼 스킨보다 구조를 우선한다. 최종 이미지만 통합 렌더를 요청한다.  
2. **확정값만 주입**: 후보 상태(미확정) 텍스트는 다음 단계에 넣지 않는다.  
3. **사용자 원문과 시스템 제약 분리**: 분야·키워드는 사용자 입력. 안전·형식·슬롯 스키마는 시스템 프롬프트.  
4. **출력 스키마 고정**: 각 단계는 파싱 가능한 구조(제목, 설명, 역할별 색, 프리뷰 에셋 핸들)를 반환해야 UI가 깨지지 않는다. 파싱 실패 = 생성 실패 → 환급.  
5. **재현 메타**: 모델명, 프롬프트 버전, 시드(가능 시), 단계 ID를 generation 레코드에 저장한다. 사용자에게 모델 내부 프롬프트 전문을 보여 줄 필요는 없다.

### 10.2 단계별 컨텍스트 누적

| 단계 | 반드시 포함 | 포함하지 않음 |
| --- | --- | --- |
| 컨셉 | 분야, 키워드 | 팔레트, 레이아웃, 최종 픽셀 |
| 팔레트 | 분야, 키워드, **확정 컨셉** | 와이어 구조, 컴포넌트 스펙 |
| 와이어프레임 | 위 + **확정 팔레트**(대비·역할 힌트) | 최종 포토리얼 브랜드 아트 |
| 컴포넌트 | 위 + **확정 와이어 슬롯** | 무관한 화면 템플릿 |
| 최종 이미지 | 위 전부 + “한 장의 UI 화면” 지시 | 확정과 모순되는 새 컨셉/색 |

컨텍스트가 비면 해당 단계 API는 4xx로 거절하고 크레딧을 쓰지 않는다.

### 10.3 실패 / 재시도

- 타임아웃, 5xx, 스키마 불일치, 에셋 0건: **실패 + 전액 환급 + 재시도 CTA**.  
- 부분 성공(3개 중 1개만 파싱): **실패로 간주**하고 사용자에게 불완전 후보를 확정 대상으로 넣지 않는다(**가정**).  
- 동시 요청: 프로젝트+단계 단위로 단일 in-flight. 두 번째 요청은 409 또는 대기.  
- 재시도는 동일 컨텍스트로 새 generation ID를 발급한다.  
- 사용자 중단(페이지 이탈): 서버 작업은 완료될 수 있음. 완료 시 저장, 실패 시 환급. 재진입 시 상태 동기화.

### 10.4 안전 / 저작권

- 입력·출력 모두 유해/성인/혐오/미성년 성애화 등 금지 카테고리 필터. 차단 시 미과금 또는 즉시 환급.  
- 프롬프트에 **특정 상용 브랜드 로고·캐릭터·유명 UI를 복제**하라는 명시가 있으면 거절하거나 일반화한다. 완벽한 탐지는 보장하지 않으며 가드레일로 명시.  
- 출력 화면 고지(가정): “생성물은 참고용 프로토타입이며, 제3자 권리·상표 사용은 사용자 책임.”  
- 사용자 업로드 학습(P2) 전, 업로드 파일이 학습에 쓰이는지 여부를 별도 동의로 분리한다. MVP는 업로드 학습 없음.  
- 운영: 차단 로그(입력 해시, 사유 코드, userId)를 남긴다. 원문 프롬프트 장기 보관 기간은 법무 오픈 이슈.

### 10.5 품질 게이트 (제품)

- 최종 이미지는 스냅샷의 팔레트 역할색이 **프롬프트에 명시**되어야 한다. 자동 색 검증(픽셀 샘플)은 v1.1 Could.  
- 와이어프레임 단계는 본문 카피보다 **블록 구조**가 보이도록 지시한다.

## 11. 비기능 요구사항

### 11.1 성능

- 입력 저장, 확정, 목록 조회: p95 **2초** 이내 (생성 제외).  
- 단계 후보 생성: p95 **45초** 이내, 초과 시 실패+환급.  
- 최종 이미지: p95 **90초** 이내, 초과 시 실패+환급.  
- 로딩 중 단계명·경과 상태를 보여 준다. 빈 화면 금지.

### 11.2 보안

- 인증된 요청만 생성·원장 변경.  
- 프로젝트는 소유자만 CRUD (P1 공유는 토큰 스코프 read).  
- 서버 측에서 크레딧 검사. 클라이언트 잔액은 신뢰하지 않음.  
- 환경 변수로만 모델 API 키 관리. 브라우저에 비밀키 금지.  
- **가정**: Supabase RLS로 owner 격리. 세부 정책은 구현 계획.

### 11.3 비용

- 사용자당 일일 생성 횟수 상한(**가정**: 무료 계정 20 generation/일, 최종 이미지 포함 카운트 방식은 오픈 이슈)으로 남용·원가 폭주를 막는다.  
- 상한 도달 시 크레딧이 있어도 생성 거절 + 안내.  
- 모델 단가 대비 N 크레딧 매핑은 월 1회 이상 원가 리뷰(운영 프로세스, 제품 스펙 외).

### 11.4 접근성

- 주요 CTA·스텝퍼·후보 선택은 키보드로 완료 가능.  
- 확정/잠금/stale은 색만으로 구분하지 않고 텍스트·아이콘을 병기.  
- 이미지 후보에 짧은 alt(컨셉 제목 등).  
- 목표: 핵심 플로 WCAG 2.2 AA에 근접. 전체 감사는 출시 게이트에서 샘플 점검.

### 11.5 다국어

- MVP UI·오류·온보딩·빈 상태 **한국어 우선**.  
- 사용자 키워드는 한/영 혼용 입력 허용.  
- 생성 모델 프롬프트 언어는 한국어 입력을 유지하되, 모델이 영어 메타를 쓰더라도 UI 라벨은 한국어.

### 11.6 브라우저 / 플랫폼

- 최신 Chrome, Safari, Firefox 데스크톱.  
- 쿠키 세션 또는 동등한 인증.  
- IE 미지원.

### 11.7 감사·관측

- 생성 요청, 성공/실패, 크레딧 차감/환급, 안전 차단을 이벤트 ID로 추적.  
- PII를 프롬프트 로그 기본 수집에서 최소화(보관 정책은 오픈 이슈).

## 12. 성공 지표 (북극성 + 가드레일)

### 12.1 북극성 (North Star)

**주간 “완료 프로젝트” 수**: 중간 4단계 확정 + 최종 프로토타입 이미지 1장 이상이 저장된 프로젝트 수 (유저당 중복 가능, 대시보드는 unique user도 병기).

이유: 원샷 생성이 아니라 **단계 합의 완료**를 측정한다.

### 12.2 선행 지표

- 가입 → 프로젝트 1개 생성 비율 (24h).  
- 프로젝트 생성 → 컨셉 1회 확정 비율.  
- 컨셉 확정 → 최종 이미지 완료까지의 중위 시간, 중위 생성 횟수.  
- 최종 이미지까지 도달한 세션 비율 (Activation).

### 12.3 후행 지표

- D7 재방문 사용자 중 기존 프로젝트 재오픈 비율.  
- 무료 크레딧 소진 후 7일 내 유료 전환율 (P1 결제 이후).  
- 프로젝트당 최종 이미지 재생성 횟수 (품질 불만 프록시).

### 12.4 가드레일

| 가드레일 | 임계(가정) | 대응 |
| --- | --- | --- |
| 생성 실패율 | 주간 > 15% | 모델/타임아웃 롤백, 환급 큐 점검 |
| 크레딧 원장 불일치 티켓 | 주간 > 0건 미해결 24h | 생성 중단 후 원장 수정 |
| 안전 필터 오탐으로 정상 업무 차단 | 정성 + 샘플 | 정책 튜닝 |
| 사용자당 원가 | 무료 유저 월 원가 > 지급 크레딧 설계치 150% | 일일 상한·N 조정 |
| 최종 이미지 직행 시도(잠금 우회 에러) | 급증 시 | UX 카피·온보딩 강화 |

### 12.5 실험

MVP는 전체 사용자 단일 플로. A/B는 v1.1 이후. 후보 수 3 vs 5, 최종 이미지 N=5 vs 3 등은 지표가 안정된 뒤 실험.

## 13. 출시 범위

### 13.1 1차 구현 (프로토타입) — 지금 게이트

포함: 랜딩, 짧은 온보딩(선택), 프로젝트 생성(로컬), 분야/키워드, 4단계 추천·확정, 최종 이미지, 로딩/에러, 한국어 UI. 새로고침 후 같은 브라우저에서 이어서 보기(localStorage).

미포함: 인증, Supabase, DB 스키마, RLS, 크레딧 원장, 결제, 공유 링크, 댓글, variant, 내보내기, 실시간 협업.

**게이트**: 섹션 3.1 목표 1~3을 로컬에서 시나리오 테스트로 통과. 중간 단계 스킵으로 최종 생성 불가.

### 13.1a 상용화 MVP (P0-ga) — 다음 개발 게이트

포함: 인증, 프로젝트 CRUD(서버), 자동 저장·재조회, 히스토리, 크레딧 잔액·차감·실패 환급, 소유권 격리.

**게이트**: 섹션 3.1 목표 4~6. 타 사용자 프로젝트 미노출. 크레딧 부족 시 미호출.

### 13.2 v1.1

P1: variant, PNG/JSON 토큰 내보내기, 공유 링크, 팀 코멘트, 결제(구독 또는 크레딧 팩). Figma는 링크/JSON 수준.

**게이트**: 웹훅 멱등, 공유 링크 비소유자 생성 불가, 결제 후에만 잔액 증가.

### 13.3 v2

P2: 디자인 시스템 업로드, 브랜드 가이드 학습, 실시간 협업. 영문 UI. (별도 PRD)

## 14. 리스크와 가정

### 14.1 가정

1. 워크스페이스는 그린필드이며 1차 스택은 Next.js 14 + TypeScript + Tailwind + Shadcn/Radix다. **Supabase는 상용화(다음 개발)** 에서 붙인다.  
2. 이미지/멀티모달 생성 API를 사용할 수 있고, 단계별로 다른 모델 또는 같은 모델+다른 프롬프트를 쓸 수 있다. 벤더는 미정.  
3. 1차는 결제·크레딧 없이 워크플로를 검증한다. 상용화에서 가입 지급 20크레딧과 원장을 넣는다.  
4. 한 프로젝트 = 한 대표 화면 플로. 멀티 스크린 플로는 v2.  
5. 후보 기본 3개, 크레딧 N은 섹션 7.0 표(상용화).  
6. 한국어 사용자 비중이 초기 Traction의 전부다.

### 14.2 리스크

| 리스크 | 영향 | 완화 |
| --- | --- | --- |
| 단계와 무관한 최종 이미지(컨텍스트 무시) | 핵심 가치 붕괴 | 스냅샷 강제, 최종 단계 잠금, 품질 샘플 리뷰 |
| 생성 원가 > 무료 크레딧 가치 | 적자, 한도 남용 | 일일 상한, N 조정, 실패 환급만 허용 |
| 저작권·상표 유사 출력 | 법적·브랜드 | 필터, 고지, 브랜드 복제 거절, 법무 약관 |
| 크레딧 선차감 후 상태 불일치 | 신뢰 상실, CS 폭주 | 원장 진실원, 실패 환급, 재진입 동기화 |
| 와이어프레임이 그냥 예쁜 목업이 됨 | 개발자 페르소나 실패 | 단계 프롬프트 단일 책임, 디자인 QA |
| 모델 지연/장애 | 활성화 하락 | 타임아웃·환급, 상태 표시, 벤더 이중화는 이후 |
| 결제 없이 GA 시 원가 개방 | 남용 | 초기는 초대제 또는 일일 상한 강화 |
| Vue 선호 vs Next 워크스페이스 규칙 | 구현 혼선 | 본 제품은 Next.js 가정으로 고정. Supabase는 상용화 |

## 15. 미결 질문 (Open Questions)

구현 전에 제품/사업/법무가 답해야 한다. 선택지 형태.

1. **인증 방식**: 상용화 단계에서 결정. 1차는 인증 없음. (매직링크 / 이메일+비밀번호 / Google OAuth)  
2. **분야 입력**: 고정 프리셋만인가, 자유 텍스트인가, 프리셋+기타인가?  
3. **분야/키워드 변경 시**: 이후 단계만 무효화인가, 경고 후 전체 재확정인가?  
4. **크레딧 N·가입 지급 20**을 확정하는가, 알파 원가 측정 후 조정하는가?  
5. **일일 생성 상한**을 무료/유료에 어떻게 다르게 둘 것인가? 상한이 크레딧과 이중인가?  
6. **최종 이미지 화면 수**: MVP는 1장(한 화면)으로 고정인가, 랜딩+대시보드 등 멀티 화면인가?  
7. **Figma 산출물(P1)**: PNG+JSON으로 충분한가, 서드파티 “Figma 파일 생성” API가 필요한가?  
8. **요금제(P1)**: 구독 월 크레딧 vs 크레딧 팩만 vs 둘 다? 무료 잔액 리필 주기(없음/매월)는?  
9. **생성물 권리**: 사용자에게 상업적 사용권을 주는가, 서비스는 모델/개선에 출력을 쓰는가?  
10. **프로젝트 삭제/복구**, PrototypeAsset 보관 개수(20?)와 스토리지 비용 한도는?  
11. **팀 공간**: P1 댓글은 동일 계정 공유인가, 워크스페이스(조직) 모델인가?  
12. **모델 벤더 선정**과 단계별 모델 분리 여부(텍스트 구조 vs 이미지) — 기술 스파이크 후 결정.
